PRINCIPLE 1 AND THE DISTILLER

The "by construction" claim is too strong and we are removing it. A successful trace gives provenance and achievability; necessity, compression and equivalence quality depend on the distiller and validator, so they must be measured.

We audited 100 TaskSpecs by hand from the released corpus: 264 retained tool_effect checkpoints, 200 of the non-retained calls, 67 listed alternatives.

| audited | result | Wilson 95% CI |
|---|---|---|
| grounded in a successful call | 261/264 = 98.9% | 96.7 - 99.6 |
| of those, necessary to the goal | 261/261 = 100% | 98.5 - 100 |
| non-retained calls redundant or irrelevant | 188/188 resolved = 100% | 98.0 - 100 |
| specs missing a required effect | 1/100 = 1% | 0.2 - 5.4 |
| listed alternatives effect-equivalent | 67/67 = 100% | 94.6 - 100 |
| specs valid as written (4 minor, 1 permissive) | 95/100 | |

Twelve further non-retained calls were unresolved, mostly recovery after a failure; counting all twelve as errors gives 94%. The missing effect was never executed in the reference trace, so it is a reference-validation miss.

The same compression appears at corpus scale: 5.63 recorded calls become 2.52 required checkpoints, chains of five or more 13.5 to 4.1. Distiller output is also not accepted blind: a fourth-family validator and trace check discard a quarter of parseable output.

TOOL DISCOVERY

You are right that our setup isolates tool use from tool discovery. We have now measured the cost. On 150 tasks balanced across chain depth we replaced the curated pool with retrieval over the entire 1,168-tool catalog, exposing only the top eight tools by embedding similarity, against the released verdicts for the same model and tasks.

| chain depth | retrieval, full catalog | curated pool | delta |
|---|---|---|---|
| short (1-2) | 64.0% | 62.0% | +2.0 |
| medium (3-4) | 30.0% | 74.0% | -44.0 |
| long (5+) | 16.0% | 36.0% | -20.0 |
| all 150 | 36.7% | 57.3% | -20.7 |

The curated column is one model, one attempt, 50 tasks per bucket, so its short-medium ordering is within noise; the paper's curve is pass^3 over 24 models.

The cost is entirely compositional: single-step tasks are unaffected and the retrieval curve stays monotone. Of the 274 unmet checkpoints, 64% are tools the agent never called, the discovery failure you predicted. So open-universe exposure adds no difficulty axis and did not manufacture our chain-length result: it sharpens it.

STATEFUL TASKS AND REFRESH

Agreed that state-changing tasks are the fragile 12%, but candidate evaluation never touches a live server. It replays the recorded world, so no candidate fails because an API was down or a table missing at scoring time. Live servers are contacted only when refreshing references, and a refresh that cannot provision the required state should quarantine the task, not count it as agent failure. We will add a preflight before a refreshed task returns.

On your first question, the submitted study does not separate drift from transient failure. Its classifier is three-way, identical, drifted, broken, with a single retry, so broken conflates decay with timeouts and rate limits and is an upper bound on persistent breakage. The Wikipedia row shows we treat rate limits as transient: nine of ten traces were excluded on that basis. The separation we will implement is mechanical: retry transient errors with backoff; schema drift only when discovery shows a changed or removed tool on a reachable server; state decay when the schema is intact but a record is gone; quarantine the rest.

THE JUDGE AND THE 0.75 THRESHOLD

No reported result depends on any LLM judgment. The leaderboard, the rankings, the chain-length curve and every category number come from deterministic checks alone; the judge is off by default and was never enabled for the paper, so prompt sensitivity and judge-family variance cannot touch a reported claim. To be exact about scope: that covers scoring, not construction. The distiller and validator are LLMs, which is why we measured their output above.

The 0.75 threshold is not the judge; our wording conflated two mechanisms and we will fix it. It belongs to replay: a deterministic argument matcher comparing a candidate's arguments to a recorded call field by field, with a string-similarity fallback, serving the cached result above the threshold. No model is involved, so it has no prompt or family sensitivity.

On the one subset where we enabled it, 200 cells at one attempt, it was invoked on 120 Tier-1 failures and overrode 7, moving 3 cells, 96 of 200 to 99. Tier-2 can only turn a failure into a pass, so every reported number is the conservative end of what any judge setting could give. Those records carry no category label; we will replay them through several judge families and report per-category rates in the camera-ready.
