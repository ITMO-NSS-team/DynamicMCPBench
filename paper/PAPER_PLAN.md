# DynamicMCPBench — Paper Plan (write-from-this)

**Venue:** EMNLP 2026 Industry Track. 6 pp main; **References + Appendix are
unlimited** → secondary tables/experiments go to the Appendix. Mandatory
Limitations; double-blind; ACL template.

**Thesis (framework-first).** We ship a **reusable framework**, not a fixed
dataset: point it at *your own* Model Context Protocol (MCP) servers and *your
own* models; it forward-explores live servers, distills real successful
trajectories into path-agnostic effect checkpoints, and scores agents on
**effects, never on the final answer**. The study is a **demonstration**: we
took **24 models** and **121 servers**, generated **50 tasks per category × 15
categories = 750**, with one generation setup, and **validated all 750** results
of the strongest local model.

## 2. Experimental design choices — explained and justified **in words** — **(MAIN)**
*(NO CLI flags, NO command names, NO code internals anywhere in the paper. State each choice as a design decision and say why it is the right one. Quantities are reported as methodology, never as code.)*

**Generation — what we chose and why:**
- **Forward, trace-grounded generation.** We form a realistic user goal, let an agent solve it live on the real servers, and turn the successful trajectory into the task. *Why:* every tool in the task was actually used to reach the goal, so there are no spurious "required" tools and every task is provably achievable — unlike back-instructing questions from a tool graph.
- **Balanced category coverage.** Fifteen task categories span single-tool requests, long cross-server chains, and the specific confusions we probe (true alternatives, look-alikes, prerequisites, recovery, decoys, …). We keep an **equal number of tasks per category** so no category dominates the aggregate and per-category comparison is fair.
- **Controlled difficulty span.** Seed difficulty is scaled so the benchmark deliberately covers short to long dependency chains — a controlled difficulty axis rather than an accidental one.
- **Diverse phrasing.** Goals are written from varied user personas for linguistic and intent diversity.
- **Multi-family authorship.** Tasks are authored by many model families so the corpus is not shaped by any single model's idiosyncrasies (verified to leave no systematic self-preference, §1.12).

**Evaluation — what we chose and why:**
- **Deterministic replay of the recorded world.** Every model is evaluated against the same recorded environment rather than the live, drifting world. *Why:* differences then reflect the agent, not network or state changes — the precondition for fair cross-model comparison and exact reproducibility.
- **Repeated attempts for reliability (pass^3).** Each task is attempted three times and counts as solved only if all three succeed. *Why:* a single attempt overstates reliability for stochastic agents; the all-attempts criterion reports dependable capability.
- **Controlled tool pool with alternative distractors.** The candidate is offered the tools it needs plus a fixed set of distractors, **half of which are same-name tools on other servers**. *Why:* a controlled, identical-across-models stress on server attribution — non-trivial without being adversarial.
- **An action budget large enough for the longest chains.** *Why:* failures then reflect capability, not a truncated budget.
- **No description or retrieval confounds on the main result.** Tool descriptions are used as-is and all tools are exposed directly (no rewriting, no retrieval filtering). *Why:* the headline measures the agent, not a description-normalizer or a retriever; description-quality and tool-exposure variants are kept as **separate controlled ablations**.
- **Effect-based, answer-agnostic scoring.** A deterministic effect check decides pass/fail; a second-tier judge only rescues effect-equivalent alternatives; the final answer is never graded. *Why:* on live, stateful data the answer is unstable, but the effects are verifiable.

All choices follow the same four principles: **fairness/comparability, reproducibility, reliability, and freedom from confounds.**

## 6. Limitations & Future Work
**Limitations:** the scorer is **conservative** — it can fail valid alternative trajectories, so reported accuracies are **lower bounds**; 12% of tasks are stateful-write (sandbox-gated); reliability on the near-unanimous validity axis is paradox-affected (report AC1); human validation covers the single strongest local model; substrate leans English / public-API.
**Future Work (from the validation pass):**
1. **Stateful setup at generation time** — some otherwise-valid tasks fail because referenced state is absent (a database table or file does not exist at eval time); next iteration provisions a per-task container/state at question creation so stateful tasks are reproducible.
2. **A clarification node before distillation** — agents that ask a clarifying question can fail even though clarifying is reasonable, penalizing "asks-first" models; add a refinement step (goal → explore → **refine question** → distill) so specs account for legitimate clarification.
