# Tool-exposure matrix over the open universe (e9.1)
- status: planned
- result: —

Camera-ready item **3.1** (`docs/CAMERA_READY.md`), promised to reviewers RJAT and
sJ7917. `e8.11` answered the reviewers' objection with a single point: one model
(`qwen3.7-max`), one retriever (embedding top-8), one slice, one attempt. What we
owe is the surface around that point — the flat full-catalog condition, the
hierarchical router, other `rag-k`, more models, and pass^3.

## Question / hypothesis

When the curated pool is removed and the agent must find its tools in the full
1,168-tool catalog, how much of the measured drop (57.3% → 36.7% for
`qwen3.7-max` at top-8) is a property of *the benchmark's difficulty* rather than
*that one retrieval configuration*?

- **H1 (retrieval budget).** Success rises monotonically with `rag-k` and does not
  recover the curated level even at k=32, because the binding constraint is
  retrieving the right tool at all, not ranking among a few.
- **H2 (depth interaction).** The gap stays concentrated in medium and long
  chains at every k. Short chains are near-parity because one good retrieval
  suffices; long chains compound per-step retrieval risk.
- **H3 (architecture).** A hierarchical router (pick a server, then its tools)
  beats flat top-k retrieval at equal exposure, because server identity is a
  lower-entropy decision than tool identity.
- **H4 (model).** The ordering of models is preserved between the curated pool
  and the open universe (rank correlation high), i.e. open-universe exposure
  lowers the level without reshuffling the leaderboard.
- **H5 (flat feasibility).** The literal flat full-catalog condition is not
  runnable for most of the pool: the catalog serialises to ~292k tokens of tool
  schema, which exceeds the context window of `kimi-k2.6` (262,144),
  `glm-5.1` (204,800) and `claude-haiku-4.5` (200,000). Only the 1M-context
  models (`qwen3.7-max`, `minimax-m3`) can be offered the whole catalog.

H5 is registered as a *finding to report*, not a hypothesis to test: it follows
from published context limits and the measured catalog size, and it is the reason
the flat row of the matrix is deliberately incomplete.

## Method (+ reproduce command)

**Tasks.** 150 specs drawn from the released 750-task leaderboard slice, balanced
50/50/50 across reference-chain depth (short 1-2, medium 3-4, long 5+),
`random.seed(0)`. The 750-slice is recovered from the released per-run verdicts
(a task is in the slice iff all eight leaderboard models have a verdict for it);
depth is the number of `call_tool_agent` steps in the spec's source trace. `e8.11`
used the same rule but did not commit its task ids, so the subset is rebuilt by a
now-committed deterministic builder:

```bash
uv run python scripts/cr_subset.py --corpus hfdl --n-per-bucket 50 \
    --out manifests/subsets/cr150.jsonl --ids-out manifests/subsets/cr150.ids.txt
```

The 150 ids are committed as `manifests/subsets/cr150.ids.txt`; the spec payload
itself stays out of git and is regenerated from the released corpus.

Because the subset is rebuilt rather than restored, the `qwen3.7-max` / `rag:8`
cell is **re-run as a reproduction check** on `e8.11`'s 36.7% rather than copied.

**Conditions.** All under `--pool full`, i.e. the entire catalog reconstructed
from the reference traces, with no curated distractor pool:

| axis | values |
|---|---|
| retrieval budget | `rag-k` ∈ {4, 8, 16, 32} |
| architecture | `rag` (embedding top-k), `hier` (router picks a server) |
| flat | whole catalog in one tool list — 1M-context models only |
| models | `minimax-m3`, `kimi-k2.6`, `claude-haiku-4.5`, `qwen3.7-max` |
| attempts | 1 for the sweep; 3 (pass^3) at `rag:8` |

**Scoring.** Deterministic replay against the released reference traces
(`--replay --reference-traces`), Tier-1 effect checkpoints only, no LLM judge —
identical to the leaderboard, so the curated baseline is comparable without
spending baseline compute. Budget 12 tool calls per task, as in `e8.11`.

**Baseline.** The released per-run verdicts for the same model on the same task
ids (`leaderboard_e8.10d/verdicts/evals_*.jsonl`). Comparison is matched
task-for-task.

```bash
uv run python scripts/run_cr_matrix.py \
    --models minimax/minimax-m3,moonshotai/kimi-k2.6,anthropic/claude-haiku-4.5,qwen/qwen3.7-max \
    --conditions rag:4,rag:8,rag:16,rag:32,hier --repeat 1 --lanes 1,2,3 --shards 9
uv run python scripts/cr_compare.py --evals 'evals/cr/*.jsonl' --corpus hfdl
```

Runs are staged in waves and the per-task cost is remeasured after each wave;
the wave boundary is a spend checkpoint, not a scientific one, and the analysis
is over whatever cells complete.

## Decision rule (pre-registered)

Registered before any cell beyond the 3-task pipeline smoke was run.

- **H1 positive** iff success at k=32 exceeds success at k=4 by ≥10 points with
  non-overlapping Wilson 95% intervals, **and** k=32 remains ≥10 points below the
  matched curated baseline. Negative if k=32 reaches within 5 points of curated
  (the deficit is a retrieval-budget artefact, and the open-universe claim in the
  paper must be narrowed to small k). Neutral otherwise.
- **H2 positive** iff, pooled over k, the curated-minus-open gap in the long
  bucket exceeds the gap in the short bucket by ≥15 points. Negative if the short
  bucket's gap is the larger. Neutral otherwise.
- **H3 positive** iff `hier` beats `rag:8` by ≥5 points pooled over models with
  non-overlapping intervals; negative if `rag:8` beats `hier` by ≥5 points;
  neutral otherwise.
- **H4 positive** iff Spearman ρ between the curated and open-universe model
  orderings is ≥0.8; negative if ρ < 0.5; neutral otherwise. With four models
  this is descriptive, and will be reported as such.
- A cell that cannot run for a mechanical reason (context overflow, exhausted
  key lane) is reported as **not runnable** with the reason, never silently
  dropped or replaced by a cheaper substitute.

Reporting `neutral` or `negative` is a valid outcome of this experiment and is
committed either way; the paper text then states the narrower claim.

### Post-hoc analysis: separating retrieval loss from distraction

**Not pre-registered.** Added after seeing the matrix, to explain it. Reported as
exploratory.

The matrix alone cannot say *why* success falls in the open universe. Two
mechanisms predict the same shape: the retriever fails to surface the needed tool
(retrieval loss), or the tool is on screen and the agent still fails to pick and
drive it (distraction). The design separates them, because each can be held fixed
while the other varies:

`scripts/cr_recall.py` replays the exact `rag_surface` ranking offline (same
`"name: description"` text, same cosine, same index tie-break) and asks how often
each `tool_effect` checkpoint is *reachable* — at least one member of its
`equivalence_set` exposed. Under `--pool full` the required tools are guaranteed
to be in the pool, so `flat` has reachability 1.0 by construction.

| k | checkpoint recall | tasks fully reachable | short / medium / long |
|---|---|---|---|
| 4 | 43.2% | 36.7% | 76.0 / 42.5 / 32.4 |
| 8 | 57.7% | 48.0% | 82.7 / 55.9 / 50.2 |
| 16 | 68.9% | 62.7% | 92.0 / 70.9 / 59.8 |
| 32 | 77.9% | 75.3% | 93.3 / 84.3 / 68.9 |
| flat | 100% | 100% | guaranteed by `--pool full` |

Reachability is a property of the retriever and the tasks, not of the candidate,
and indeed comes out identical across all four models — a consistency check on
the computation.

**Reachability is a hard gate.** Over the 1,064 single-attempt task-cells whose
tasks the map calls unreachable, the number that passed is **zero**. Adding the
three-attempt cells, it is **1 in 1,905 — 0.05%**, and that one is a single task
at `k=8` that the map calls reachable at `k=16` and `k=32`, where it also passes.
The cause of the flip is not established and none is asserted; the measured rate
is what everything downstream inherits. Passing effectively requires the tool to
have been shown, which is what licenses reading the reachability column as a
ceiling rather than as a correlate.

(One spec in the subset carries only `value_produced` checkpoints. It demands no
particular tool, so retrieval cannot gate it and it is counted as vacuously
reachable. Scoring it as unreachable instead — the first version of this analysis —
manufactured four spurious "passed while unreachable" cells.)

That licenses the decomposition, holding one factor fixed at a time
(`minimax-m3`, matched task-for-task):

| condition | tools shown | reachability | pass |
|---|---|---|---|
| curated (`--pool target --pool-size 8`) | ~8 | 100% | 44.0% |
| `rag:8` | 8 | 48.0% | 24.0% |
| `rag:32` | 32 | 75.3% | 36.7% |
| `flat` | 1,168 | 100% | 36.0% |

- curated → `rag:8` holds the number of tools shown at 8 and drops reachability
  to 48.0%: **−20.0 points, the cost of retrieval loss**.
- curated → `flat` holds reachability at 100% and raises the tool count from 8 to
  1,168: **−8.0 points, the cost of distraction alone**.
- `rag:32` ≈ `flat` (36.7 vs 36.0) is then not a coincidence: at k=32 the
  remaining retrieval loss and the avoided distraction very nearly cancel.

  failure against 0.17–0.36 per reachable one — a 6–14× separation holding on all

  it should mean.

  way: 0.06–0.21 unreachable against 0.23–0.45 reachable. The agent found the tool

families, two retrieval budgets, E6 confined to 2.12–2.43. Nothing about the
candidate moves it, because it is not measuring the candidate.

is reachable, yet E6 is 0.85 — three times the 0.29 of the comparable reachable
failures at `rag:32`. **That is the 8-point distraction cost as a behaviour**: the
agent goes tool-blind in the presence of the tool, because it is shown 1,168 of
them. Distraction does not manifest as picking a wrong tool; it manifests as
failing to see the right one.

### Post-hoc analysis: why `hier` plateaus

**Not pre-registered.** Same status as above.

`hier_surface` exposes exactly one server's tools, so a task whose `tool_effect`
checkpoints cannot all be satisfied from a single server is unreachable under it
*however good the router is*. That ceiling depends only on the tasks, so it can be
computed with an oracle router that always picks the best possible server:

| | tasks a single server suffices for |
|---|---|
| overall | **70.7%** |
| short (1-2) | 82.0% |
| medium (3-4) | 72.0% |
| long (5+) | 58.0% |

44 of the 150 tasks draw on two or more servers (distribution over distinct
servers available: 1→105, 2→32, 3→6, 4→3, 5→1, 6→2).

This explains the plateau without appealing to router quality. `hier` measured
32.7% on both models against an oracle ceiling of 70.7%; `rag:32` measured 36.7%
against a reachability of 75.3%. The two architectures convert their reachable
tasks at nearly the same rate (0.46 vs 0.49) — `hier` is not worse at using what
it shows, it simply shows a structurally capped set. The design implication is
concrete: a router that selects *k* servers rather than one would raise the
ceiling, and is the version worth testing next.

**This contradicts H1's stated rationale.** H1 was registered on the premise that
"the binding constraint is retrieving the right tool at all". Beyond k=32 that is
false: `flat` adds 25 points of reachability and **zero** points of success. The
constraint above k=32 is selection, not retrieval. H1's *verdict* is decided by
its registered rule (see Result); this note concerns its reasoning, which the data
does not support.

**Limitation.** The distraction cost is measured on `minimax-m3` only, because
`flat` needs a 1M-token context (H5). Confirming that 8 points is not a property
of one model requires the `qwen3.7-max` `flat` cell.

Reproduce:

```bash
uv run python scripts/cr_recall.py --corpus hfdl --k 4,8,16,32
```

### Post-hoc control: was the call budget masking the exposure effect?

**Not pre-registered.** This control was added after seeing the matrix, to test an
objection raised against it, and is reported as exploratory.

The objection: every cell runs at a 12-call budget, but 44% of long-bucket tasks
have a reference chain deeper than 12 (max 33). If the budget truncates agents
before they can act on retrieved tools, the long-bucket collapse would be an
artefact of the ceiling rather than of exposure, and H2 would be measuring the
wrong thing.

Re-ran the 50 long-bucket tasks of the subset on `minimax-m3` / `rag:32` at
budget 30, matched task-for-task (`evals/cr_budget30/`, $1.13):

| | budget 12 | budget 30 |
|---|---|---|
| pass | 20.0% | 18.0% |
| successful tool calls, mean | 4.7 | 5.1 |
| **tasks reaching the budget** | **5 / 50** | **0 / 50** |
| total calls incl. failed, mean / max | 11.3 / 47 | 13.6 / 102 |
| E3 / E6 / E7 | 43 / 73 / 19 | 39 / 69 / 24 |

**Negative — the objection does not hold.** Raising the ceiling 2.5× moved pass
rate by −2.0 points (one fail→pass, two pass→fail, i.e. run-to-run noise) because
at budget 30 *no task reached the budget at all*, and at budget 12 only five did.
The agent stops itself at ~5 successful calls out of 30 permitted; it is not being
truncated, so the long-chain gap cannot be attributed to the ceiling.

The same table shows where the effort goes instead: 13.6 attempted calls per task
yield 4.7–5.1 successful ones. Roughly two thirds of the agent's calls fail
outright, which is `E6` (tool_blindness) observed as behaviour rather than as an
end-state label — the agent is not stopping early because it is satisfied, it is
stopping after repeatedly failing to invoke tools it was shown.

Reproduce:

```bash
uv run python scripts/run_cr_matrix.py --models minimax/minimax-m3 \
    --conditions rag:32 --subset manifests/subsets/cr_long50.jsonl \
    --budget 30 --out-dir evals/cr_budget30 --lanes 1,2,3 --shards 6
```

### Post-hoc analysis: ordering survives, but the field collapses

Not pre-registered — written after seeing H4 return POSITIVE on every condition,
including the one where the benchmark had almost stopped working. Reproduce:
`uv run python scripts/cr_spread.py` (writes `docs/experiments/data/e9.1_spread.json`).

H4 asks whether open exposure preserves the *ordering* of models. Spearman rho is
scale-free, so it cannot see how far apart the models are: a condition may rank the
field perfectly while compressing it into a band narrower than the confidence
intervals. That is not a hypothetical here — it is what `rag:4` does.

| condition | models | spread | curated spread, same models | retained | top margin | rho(skill, loss) |
|---|---|---|---|---|---|---|
| `rag:4`  | 4 |  6.0 | 16.7 |  36% | 1.3 | +1.000 |
| `rag:8`  | 4 |  9.3 | 16.7 |  56% | 6.0 | +1.000 |
| `rag:16` | 4 | 14.0 | 16.7 |  84% | 4.7 | +0.400 |
| `rag:32` | 4 | 11.3 | 16.7 |  68% | 3.3 | +0.200 |
| `hier`   | 4 |  8.0 | 16.7 |  48% | 3.3 | +1.000 |
| curated  | 4 | 16.7 | 16.7 | 100% | 10.0 | — |

`spread` is best minus worst pass rate; `top margin` is best minus second best.
`retained` divides by the curated spread **over exactly the models in that row**,
so a row missing a candidate is not charged for the absence.

**The leaderboard survives; the resolution does not.** At `rag:4` the four models
are ranked correctly and separated by 6.0 points end to end, against 16.7 under
curation. The gap between the best model and the runner-up falls from 10.0 points
to 1.3 — well inside a single cell's ±8-point interval. H4 scores this POSITIVE.
Retention climbs steeply with the retrieval budget over the first three `rag`
conditions (36% → 56% → 84%) and then reads 68% at `k=32`. That last step is not
a reversal anyone should defend: spread is a difference of two cells each carrying
a ±8-point interval, so 14.0 and 11.3 are not distinguishable. What the row does
establish is that retention has stopped climbing — even a 32-tool surface hands
back only about two-thirds of the resolution curation provides, and `flat`, which
has no retrieval loss at all, still costs minimax 8 points. Widening the budget is
not a route back to curated discriminability.

**The cost is regressive: open exposure takes most from the models that had most.**

| condition | haiku (37.3) | kimi (42.7) | minimax (44.0) | qwen (54.0) |
|---|---|---|---|---|
| `rag:4`  | −20.7 | −21.3 | −26.0 | −31.3 |
| `rag:8`  | −16.0 | −18.0 | −20.0 | −23.3 |
| `rag:16` | −13.3 |  −9.3 | −12.7 | −16.0 |
| `hier`   |  −9.3 | −10.0 | −11.3 | −18.0 |
| `rag:32` |  −8.7 |  −8.0 |  −7.3 | −14.0 |

At `k=4` and `k=8` the loss ranks *exactly* with curated capability (rho = +1.000):
the stronger the model, the more the condition costs it. The mechanism is the one
`cr_recall.py` already established — reachability is a property of the retriever and
the task, identical across candidates — so the ceiling is shared, and a shared
ceiling binds hardest on whoever would otherwise have cleared it. The effect fades
as the budget grows: +0.400 at `k=16`, +0.200 at `k=32`, which is no relationship
at all. That is what a receding ceiling should look like — once retrieval usually
delivers the tool, what remains is distraction, and distraction has no reason to
scale with the skill of the reader. Note that rho over four points takes only five
distinct values, so the trend is the claim and the individual figures are not.

The one number in that row worth naming is qwen's −14.0, which is where H1 turns
(below). Every other model loses 7–9 points at `k=32` and qwen loses 14, so the
condition's *ordering* is preserved perfectly (H4 rho = +1.000) while its *cost*
is not proportional to anything — two rank correlations of the same cells that
answer different questions and need not agree.

**Mean pass rate is not a sufficient statistic for an exposure architecture.**
`hier` and `rag:16` are within a point of each other on mean pass rate (32.4 vs
31.7) while retaining 48% and 84% of the curated spread. Two surfaces of equal
apparent difficulty are not equally useful for telling models apart. This one is
suggestive rather than established: the difference is carried mostly by haiku
(28.0 under `hier` vs 24.0 under `rag:16`), a 4-point move at n=150, and the
per-cell intervals are ±8. It is reported because it is the direct consequence of
the H4 defect, and because a paper that recommends an exposure architecture on
pass rate alone would get this backwards.

### Post-hoc analysis: three attempts do not buy the deficit back

pass^3 at `rag:8` was pre-registered as a measurement but carries no decision
rule, so this is descriptive. Reproduce: `uv run python scripts/cr_passk.py`
(writes `docs/experiments/data/e9.1_passk.json`).

A single attempt per task cannot separate a ceiling from bad luck. If open
exposure mostly costs the agent *reliability*, three attempts should win most of
the deficit back. They do not:

| model | 1 attempt | pass@3 | curated | deficit recovered |
|---|---|---|---|---|
| haiku   | 21.1 | 24.0 | 37.3 | **18%** |
| kimi    | 25.1 | 28.0 | 42.7 | **16%** |
| qwen    | 29.8 | 34.0 | 54.0 | **17%** |

Three model families spanning 17 points of curated skill agree within two points
on the fraction. Tripling the attempt budget returns roughly a sixth of what open
exposure took; the rest is not available at any number of retries. Note how this
composes with the regressive pattern above — the recoverable *share* is flat while
the deficit itself grows with capability, so retries return 2.9 points to haiku
and 4.2 to qwen and leave the ordering distortion exactly where it was.

The variance is real, it is simply not where the deficit lives. On tasks whose
tools were retrieved:

| model | pass^3 | 1 attempt | pass@3 | retry headroom | matrix `r1` |
|---|---|---|---|---|---|
| haiku   | 40.3 | 43.5 | 48.6 | +5.1 | 44.4 |
| kimi    | 45.8 | 52.3 | 58.3 | +6.0 | 51.4 |
| qwen    | 52.8 | 62.0 | 70.8 | +8.8 | 63.9 |
| minimax _(91/150)_ | 42.2 | 54.1 | 64.4 | +10.4 | 50.0 |

qwen solves 52.8% of reachable tasks on all three attempts and 70.8% on at least
one — an 18-point band of pure run-to-run variance, with the tool on screen the
whole time. The last column is a free consistency check on the whole sweep: the
three-attempt mean re-measures the single-run matrix cell on the same tasks and
lands within two points of it every time.

The unreachable half is not tabulated as evidence. A task is unreachable exactly
when some `tool_effect` checkpoint has no callable member of its
`equivalence_set`, so it cannot pass, and `pass@3 = 0` there restates the
definition. `cr_errors.py` measures how often reality disagrees with that
definition anyway, and the figure is the one quoted with the reachability table
above: **1 pass in 1,905 attempts on tasks marked unreachable, 0.05%**. No
explanation for the single flip is asserted here.

### Validity check: the sweep was interrupted, and the servers are live

Not pre-registered. Reproduce: `uv run python scripts/cr_drift.py` (writes
`docs/experiments/data/e9.1_drift.json`).

The sweep did not run in one stretch. Shards were repeatedly lost to provider
`APITimeoutError` — the OpenAI SDK already retries a timeout twice, so a surviving
one means roughly half an hour of a stuck request — and `dmcp eval --resume`
recovered them hours later. Against static tasks this would be bookkeeping. These
tasks run against **live MCP servers**, and `dmcp refresh` exists in this codebase
precisely because such servers drift, so an interrupted cell is potentially a blend
of two substrates.

| cell | gap (min) | n after gap | observed Δ | composition control | excess |
|---|---|---|---|---|---|
| kimi / `rag:16` | 206 | 19 | +4.0 | −3.5 | +7.5 |
| kimi / `rag:4` | 326 | 26 | −16.5 | −12.3 | −4.2 |
| minimax / `rag:32` | 326 | 97 | +1.3 | +3.7 | −2.5 |
| qwen / `rag:32` | 514 | 49 | −10.9 | −12.2 | **+1.3** |
| **pooled** | | **191** | | | **−0.8** |

The control is what makes this readable. Tasks after a gap are exactly those on
the shards that died — a task-id-determined subset, not a random one — so they may
simply be harder. On kimi / `rag:4` and qwen / `rag:32` they are: uninterrupted
models drop 12.3 and 12.2 points on those same subsets. Both naive comparisons
would have reported double-digit "drift" that is almost entirely task composition,
and qwen's is the cell with the longest interruption in the whole sweep — 8.5
hours — which is exactly where a drift artefact would have shown up first if one
existed. Measuring the identical split on uninterrupted cells of the same
condition removes the confound, and controls are required to cover all 150 tasks,
since a partial cell straddles the two halves unevenly.

Pooled excess is **−0.8 points over 191 task-observations**. The same 191
observations resolve nothing below about ±7 points at 95%, so the honest statement
is *no drift was detected by a check that could only have detected a large one* —
not *the substrate was stable*. It is reported for the same reason the failures
are: a live benchmark that never checks is a live benchmark that never notices.

### Validity check: one model produced a complete cell that was not a result

Not pre-registered. Artifacts and the full probe table: `evals/cr/quarantine/README.md`.

While extending the panel beyond the registered four, `openai/gpt-5.4-mini`
returned a cell that looked finished: 150/150 records, no failed shards, the
runner reported `150 results in 12.5 min — ok`. Every record was `passed=false`.
Read as a score, **0.0** would have been the headline of this report — the weakest
model on the panel wiped out entirely by an open catalog, a far more dramatic
result than anything actually measured here.

It was not a score. `agent_call_count` was **0 on all 150 tasks** and the cell
cost **$0.00**; all 143 candidate traces carry `outcome=llm_error` with
`404 — No endpoints found that can handle the requested parameters`. The model
never ran. Probing OpenRouter directly isolates the cause to a single pair:

| request | result |
|---|---|
| `require_parameters` + `tool_choice` | OK |
| `require_parameters` + `max_tokens` | OK |
| **`require_parameters` + `temperature`** | **404** |
| `temperature`, flag omitted | OK |

That model's only provider does not accept `temperature`, and `dmcp/llm.py` sends
`provider.require_parameters=True` — a guard added in E8.10c so that a provider
cannot silently ignore the tool schema. The guard turns a silent parameter drop
into a loud refusal, which is what it is for.

The cell is therefore **excluded on technical grounds, and the model is absent
from the extended panel** — not because the number was bad but because no number
was produced. The alternative, dropping the flag, buys a cell whose provider
quietly ignores `temperature`: non-deterministic, and so not comparable with any
other cell in the matrix. Two properties of the tooling made this worth writing
down. The eval loop scores an empty trace normally, so a total API failure and a
genuinely failing agent are both just `passed=false`; and the error taxonomy does
not flag it either, since "called no tool" and "called the wrong tool" both land in
E6 — the dead cell's E6 was 421 against glm's 89, large and entirely believable.
Nothing short of `agent_call_count` distinguishes the two. The lesson is committed
as `memory/lesson_zero_score_is_not_a_score.md`.

## Defects in the registration itself

Recorded because a pre-registration is only worth anything if its failures are
reported as readily as its successes. None of these were changed after seeing
data — the rules stand exactly as written, and the verdicts they produce stand
with them.

1. **H3 specifies an unpaired test for a paired design.** `hier` and `rag:8` run
   on the same 150 tasks, so the pairing carries most of the information: a task
   hard for one condition is hard for the other. The rule asks for non-overlapping
   Wilson intervals on the two marginal rates, which discards that pairing and is
   the less powerful comparison the design supports. It also treats 600
   observations as independent Bernoulli trials when they are 150 tasks × 4
   models. A future registration should name the paired test (McNemar on the
   discordant pairs) before collecting anything. We do not substitute it here:
   swapping in a more powerful test after watching the registered one miss by
   0.1 points is the exact failure mode registration exists to prevent.

2. **H4 measures ordering and was written as though it measured discriminative
   power.** Rank correlation is invariant to how far apart the models are, so it
   returns POSITIVE on every condition — including `rag:4`, where the spread
   between best and worst model collapses from 16.7 points to 6.0 and the leader's
   margin from 10.0 to 1.3. "The leaderboard order survives" and "the benchmark
   can still tell these models apart" are different claims, and H4 only ever
   tested the first. `scripts/cr_spread.py` reports the second, post-hoc.

3. **H4's threshold is coarser than it looks.** On four models Spearman's rho can
   only take {1.0, 0.8, 0.6, …}, so "rho ≥ 0.8" is exactly "at most one adjacent
   swap". The registration acknowledged the descriptive status of a four-model
   rho, but not that the threshold quantises this hard.

4. **H1's bracket landed on a knife edge, and the field straddles it.** It calls
   positive at a ≥10-point deficit of `rag:32` against curated and negative at ≤5.
   Three models measure 7.3, 8.0 and 8.7 — inside the dead zone the rule leaves
   unlabelled — and qwen measures 14.0, which clears the bar. So the registered
   rule returns POSITIVE for one model and NEUTRAL for three on the same
   condition. Pooled over all four it reads **9.5, half a point short of its own
   threshold**. The honest report of that is NEUTRAL, and it is what the
   adjudicator prints. It would have taken one more passing task somewhere in the
   `rag:32` row to flip the headline verdict of this experiment, which is a fact
   about the rule and not about exposure. A threshold that a single task can move
   should have been a pooled effect size with an interval, registered as such.

## Result

**Classification: NEUTRAL overall** — three of the four registered hypotheses
return NEUTRAL and one returns POSITIVE. Every registered cell is 150/150.
Reproduce with `uv run python scripts/cr_decide.py`, which restricts itself to
the four candidates the registration names.

| hypothesis | quantity that decided it | verdict |
|---|---|---|
| H1 retrieval budget | rise `k=4`→`k=32` +15.3 (CIs disjoint); deficit vs curated **9.5** | **NEUTRAL** |
| H2 depth | long-bucket gap 19.5 − short-bucket gap 12.8 = **+6.8** (needs ≥15) | **NEUTRAL** |
| H3 architecture | `hier` 32.3 − `rag:8` 25.2 = +7.2 (needs ≥5) but CIs touch by 0.1 | **NEUTRAL** |
| H4 model ordering | rho ≥ +0.800 on all five conditions with ≥3 models | **POSITIVE** |

Three of those four NEUTRALs are a rule missing an effect that is plainly there,
not an absence of effect, and the report says so rather than rounding in either
direction:

- **H1.** Every model improves substantially with retrieval budget (+12.0 to
  +18.7 from `k=4` to `k=32`) and every model stays below curated at `k=32`. The
  deficits are 7.3 / 8.0 / 8.7 / 14.0, pooling to 9.5 — half a point under the
  threshold, and inside the 5–10 band the rule declines to label. One additional
  passing task would have flipped it.
- **H2.** Depth costs what the hypothesis said it costs, in the direction it
  said: the curated-to-open gap is 19.5 points on long chains against 12.8 on
  short ones. The registered margin of 15 was simply set far above the real
  effect of ~7.
- **H3.** `hier` beats `rag:8` by 7.2 points, clearing the 5-point margin; the
  intervals overlap by 0.1 of a point, and the rule requires both.
- **H4** passes everywhere and is the least informative verdict in the table —
  see defect #3 and the discriminability analysis. `rag:4` preserves the ordering
  perfectly while compressing the field from 16.7 points to 6.0.

The load-bearing findings of this experiment are the post-hoc ones, and they are
labelled as such throughout: the retrieval/distraction decomposition
(−20.0 vs −8.0 points), its independent confirmation in the error taxonomy
(E6 6–14× higher on unreachable failures), the regressive cost at tight budgets
(rho = +1.000 at `k=4` and `k=8`), and the collapse of discriminability that no
registered rule was written to detect.

## Conclusion & implication

**Curated tool exposure is not a neutral experimental convenience — it is the
larger part of what a curated-pool agent benchmark measures.** Moving the same
150 tasks, the same agents and the same effect-based scoring from an 8-tool
curated pool to a retrieval surface over 1,168 tools costs 16–31 points of pass
rate depending on the budget, against a curated baseline of 37–54. No registered
threshold was needed to see that; it is the first column of the matrix against
every other column.

Three consequences for the benchmark this repository is building:

1. **Report the exposure condition or the number means nothing.** A pass rate is
   a statement about a model *and a tool surface*. `minimax-m3` scores 44.0, 36.7
   or 18.0 on identical tasks depending only on how tools were presented — a
   range wider than the entire spread between the best and worst model under
   curation.
2. **Open exposure is regressive at realistic budgets, so it distorts
   comparisons rather than merely deflating them.** At `k=4` and `k=8` the loss
   ranks exactly with capability: reachability is a property of the retriever, so
   the ceiling is shared, and a shared ceiling binds hardest on whoever would
   otherwise have cleared it. The leaderboard order survives — which is precisely
   what makes this dangerous, since the ordering looks intact while the margins
   that justify it have gone.
3. **Rank correlation is the wrong acceptance test for an exposure
   architecture.** It is scale-free and therefore blind to the failure mode that
   actually occurred. `hier` and `rag:16` differ by under a point in mean pass
   rate and retain 48% versus 84% of the curated spread. A benchmark choosing a
   surface on mean difficulty would pick the one that tells models apart worse.

The recommendation this supports is narrow and is what the camera-ready draft
should say: **the retrieval surface belongs to the benchmark, not to the agent.**
It must be specified, versioned and reported alongside results, the way the task
set is. Whether `hier` genuinely beats `rag:8`, whether the retention advantage of
`rag:16` holds up, and whether the regressive pattern survives a wider skill range
are open — the extended-panel run in the exploratory section is a first look at
the last of these and it is not registered.

What this experiment does **not** show: that open exposure is the more realistic
setting, or the better one. It shows the choice is consequential and currently
unreported. It also does not show the substrate was stable — the drift check
could only have caught a large effect, and says so.
