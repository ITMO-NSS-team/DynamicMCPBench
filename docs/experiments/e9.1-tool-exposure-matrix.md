# Tool-exposure matrix over the open universe (e9.1)
- status: planned
- result: —

Camera-ready item **3.1** (`docs/CAMERA_READY.md`), promised to reviewers RJAT and
sJ7917. `e8.11` answered the reviewers' objection with a single point: one model
(`qwen3.7-max`), one retriever (embedding top-8), one slice, one attempt. What we
owe is the surface around that point — the flat full-catalog condition, the
hierarchical router, other `rag-k`, more models, and pass^3.

## Question / hypothesis

When the curated pool is removed and the agent must find its tools in the full
1,168-tool catalog, how much of the measured drop (57.3% → 36.7% for
`qwen3.7-max` at top-8) is a property of *the benchmark's difficulty* rather than
*that one retrieval configuration*?

- **H1 (retrieval budget).** Success rises monotonically with `rag-k` and does not
  recover the curated level even at k=32, because the binding constraint is
  retrieving the right tool at all, not ranking among a few.
- **H2 (depth interaction).** The gap stays concentrated in medium and long
  chains at every k. Short chains are near-parity because one good retrieval
  suffices; long chains compound per-step retrieval risk.
- **H3 (architecture).** A hierarchical router (pick a server, then its tools)
  beats flat top-k retrieval at equal exposure, because server identity is a
  lower-entropy decision than tool identity.
- **H4 (model).** The ordering of models is preserved between the curated pool
  and the open universe (rank correlation high), i.e. open-universe exposure
  lowers the level without reshuffling the leaderboard.
- **H5 (flat feasibility).** The literal flat full-catalog condition is not
  runnable for most of the pool: the catalog serialises to ~292k tokens of tool
  schema, which exceeds the context window of `kimi-k2.6` (262,144),
  `glm-5.1` (204,800) and `claude-haiku-4.5` (200,000). Only the 1M-context
  models (`qwen3.7-max`, `minimax-m3`) can be offered the whole catalog.

H5 is registered as a *finding to report*, not a hypothesis to test: it follows
from published context limits and the measured catalog size, and it is the reason
the flat row of the matrix is deliberately incomplete.

## Method (+ reproduce command)

**Tasks.** 150 specs drawn from the released 750-task leaderboard slice, balanced
50/50/50 across reference-chain depth (short 1-2, medium 3-4, long 5+),
`random.seed(0)`. The 750-slice is recovered from the released per-run verdicts
(a task is in the slice iff all eight leaderboard models have a verdict for it);
depth is the number of `call_tool_agent` steps in the spec's source trace. `e8.11`
used the same rule but did not commit its task ids, so the subset is rebuilt by a
now-committed deterministic builder:

```bash
uv run python scripts/cr_subset.py --corpus hfdl --n-per-bucket 50 \
    --out manifests/subsets/cr150.jsonl --ids-out manifests/subsets/cr150.ids.txt
```

The 150 ids are committed as `manifests/subsets/cr150.ids.txt`; the spec payload
itself stays out of git and is regenerated from the released corpus.

Because the subset is rebuilt rather than restored, the `qwen3.7-max` / `rag:8`
cell is **re-run as a reproduction check** on `e8.11`'s 36.7% rather than copied.

**Conditions.** All under `--pool full`, i.e. the entire catalog reconstructed
from the reference traces, with no curated distractor pool:

| axis | values |
|---|---|
| retrieval budget | `rag-k` ∈ {4, 8, 16, 32} |
| architecture | `rag` (embedding top-k), `hier` (router picks a server) |
| flat | whole catalog in one tool list — 1M-context models only |
| models | `minimax-m3`, `kimi-k2.6`, `claude-haiku-4.5`, `qwen3.7-max` |
| attempts | 1 for the sweep; 3 (pass^3) at `rag:8` |

**Scoring.** Deterministic replay against the released reference traces
(`--replay --reference-traces`), Tier-1 effect checkpoints only, no LLM judge —
identical to the leaderboard, so the curated baseline is comparable without
spending baseline compute. Budget 12 tool calls per task, as in `e8.11`.

**Baseline.** The released per-run verdicts for the same model on the same task
ids (`leaderboard_e8.10d/verdicts/evals_*.jsonl`). Comparison is matched
task-for-task.

```bash
uv run python scripts/run_cr_matrix.py \
    --models minimax/minimax-m3,moonshotai/kimi-k2.6,anthropic/claude-haiku-4.5,qwen/qwen3.7-max \
    --conditions rag:4,rag:8,rag:16,rag:32,hier --repeat 1 --lanes 1,2,3 --shards 9
uv run python scripts/cr_compare.py --evals 'evals/cr/*.jsonl' --corpus hfdl
```

Runs are staged in waves and the per-task cost is remeasured after each wave;
the wave boundary is a spend checkpoint, not a scientific one, and the analysis
is over whatever cells complete.

## Decision rule (pre-registered)

Registered before any cell beyond the 3-task pipeline smoke was run.

- **H1 positive** iff success at k=32 exceeds success at k=4 by ≥10 points with
  non-overlapping Wilson 95% intervals, **and** k=32 remains ≥10 points below the
  matched curated baseline. Negative if k=32 reaches within 5 points of curated
  (the deficit is a retrieval-budget artefact, and the open-universe claim in the
  paper must be narrowed to small k). Neutral otherwise.
- **H2 positive** iff, pooled over k, the curated-minus-open gap in the long
  bucket exceeds the gap in the short bucket by ≥15 points. Negative if the short
  bucket's gap is the larger. Neutral otherwise.
- **H3 positive** iff `hier` beats `rag:8` by ≥5 points pooled over models with
  non-overlapping intervals; negative if `rag:8` beats `hier` by ≥5 points;
  neutral otherwise.
- **H4 positive** iff Spearman ρ between the curated and open-universe model
  orderings is ≥0.8; negative if ρ < 0.5; neutral otherwise. With four models
  this is descriptive, and will be reported as such.
- A cell that cannot run for a mechanical reason (context overflow, exhausted
  key lane) is reported as **not runnable** with the reason, never silently
  dropped or replaced by a cheaper substitute.

Reporting `neutral` or `negative` is a valid outcome of this experiment and is
committed either way; the paper text then states the narrower claim.
