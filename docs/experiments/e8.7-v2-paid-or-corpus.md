# E8.7 v2 — paid-OR corpus expansion (full 127-server substrate)

## Question / hypothesis

E8.7 v1 produced 178 specs on the free endpoint over the 16-server local
manifest. After the free endpoint died (2026-06-10, see E8.0d), can the
same cross-family pipeline scale the corpus toward the ~1100-spec Phase D
target on **paid OpenRouter** over the **full crawled substrate**
(`manifests/servers.json`, 147 servers / 127 with captured surfaces), at
single-digit-dollar cost and without the v1 free-endpoint error rates?

## Method

One `scripts/build_corpus.py` invocation, killed/resumed several times
(`--resume` is the contract under test as much as the corpus itself):

- **Goal-gen:** `deepseek/deepseek-v4-pro` over pre-captured surfaces
  (`data/surfaces_full.json`, 995 tools), 15 strategies × 3 complexities
  × `--per-strategy 24` → **980 goals** after caps.
- **Exploration/distillation:** 3 cross-family shards
  (explorer → distiller): deepseek → z-ai, z-ai → deepseek,
  moonshot → z-ai. `--budget 12`, `--explore-timeout 600`.
- **Validation:** 4th-family `minimax/minimax-m3` verdict per spec
  (advisory stamp under `provenance.validator`).
- Single `OPENROUTER_API_KEY` → shards dispatched sequentially
  (`--concurrency 3` capped to 1).

### Reproduce

```
uv run python scripts/build_corpus.py \
  --manifest manifests/servers.json \
  --surfaces data/surfaces_full.json \
  --goalgen-model deepseek/deepseek-v4-pro \
  --explorer-models deepseek/deepseek-v4-pro,z-ai/glm-5.1,moonshotai/kimi-k2.6 \
  --distiller-candidates z-ai/glm-5.1,deepseek/deepseek-v4-pro,minimax/minimax-m3,moonshotai/kimi-k2.6 \
  --validator-model minimax/minimax-m3 \
  --complexities simple,medium,hard \
  --per-strategy 24 --budget 12 --concurrency 3 \
  --out data/corpus_e8.7_v2 --resume
```

## Pre-registered decision rule

Positive if the run yields ≥600 validator-valid specs over ≥60 distinct
servers with a distill rate materially above v1's 57%; negative if
paid-OR cost or error rates make full-substrate generation impractical.

## Results

### Corpus

| Shard | Explorer → distiller | Specs | Traces |
|---|---|---|---|
| 0 | deepseek-v4-pro → glm-5.1 | 323 | 337 |
| 1 | glm-5.1 → deepseek-v4-pro | 323 | 347 |
| 2 | kimi-k2.6 → glm-5.1 | 313 | 330 |
| **total** | | **959** | **1014** |

- **710 / 959 validator-valid (74%)** after the rescue pass (below).
- 90 distinct servers touched; dynamism: 894 `live_read`,
  65 `stateful_write` (sandboxed substrate only).
- Strategy coverage is near-uniform (51–69 specs across all 15
  strategies); depth bins 1-2/3-4/5+ = 339/222/398; scope
  cross-server/intra-server = 435/524 (`coverage.md`).
- Distill rate ~95% of explored goals with ≥1 successful call —
  versus v1's 57% — and **zero** explorer `llm_error` rows (v1 saw
  50–67% per shard on the free endpoint).
- Direct cost ≈ **$15** on OpenRouter; wall time ≈ 3.5 days
  (sequential shards on one key; ~19–25 goals/hour).

### Validator rescue (the headline operational finding)

The first validator sweep stamped only 417/915 valid — but **339 of the
498 invalids were `non-JSON validator output` with an empty body**:
minimax-m3 under sustained load returns HTTP 200 with no content. After
making unparseable content retryable (PR #93) and re-judging the 339,
**263 (78%) flipped to valid** — almost exactly the substantive pass
rate. An eval-blind reading of the first sweep would have undercounted
the corpus by ~38%. Verdict-quality is now monitored: substantive
rejects (235 total) cite real flaws (hardcoded subtopics, baked-in
failure modes, prompt/checkpoint mismatches).

### Transient-failure taxonomy (all fixed in-flight)

| Failure shape | Symptom | Fix |
|---|---|---|
| Malformed 200 body | `JSONDecodeError` kills shard | retry in `chat()` (#88) |
| Torn/glued JSONL after hard kill | wrapper crash in provenance stamp | peel objects, drop tails (#88) |
| Rate-limited primaries → fallback provider rejects forced `tool_choice` | OR-wrapped 400, looks permanent | detect wrapper, retry w/ long backoff (#91) |
| Empty validator content | spec stamped invalid | retry non-JSON content (#93) |
| 200 with `choices: null` | `TypeError` in `chat()` | treat as transient (#95) |
| Secret-scan false positive (`…ma·sk-cdf42…` in fetched HTML) | upload refused | token-boundary lookbehind (#97) |

Shard-level retry (3×, idempotent via `--resume`) plus these client
fixes carried the final ~500 goals with no human intervention.

### Release

Merged into the shared HF dataset
(`TokenWasteGroup/DynamicMCPBench`, private) via
`scripts/merge_to_hf.py` as part `jerzypro` (v1+v2 union: 804 valid
specs / 1324 traces). Merged dataset across 4 contributors:
**1527 specs**.

## Conclusion (classification: **positive**)

The decision rule is met with margin: 710 valid specs (≥600), 90
servers (≥60), ~95% distill rate (≫57%), ~$15 (≪ the $96 Phase D eval
ceiling from E8.0d). Paid OR is strictly cleaner than the free endpoint
— the v1 error modes vanished, replaced by rarer transient shapes that
are now retried in-client. The corpus pipeline is contributor-parallel
end-to-end: generate → validate → `merge_to_hf` proved out with 4
independent contributors converging on one dataset.
