# e9.10 — The reference-validation gate: does a "successful" exploration produce every required effect?

- **status:** done
- **ledger step:** E9.10 (`docs/PLAN.md`), camera-ready commitment 4.1
- **promised to:** reviewers 1npx, RJAT, sJ7917 — *"the missing effect was never executed
  in the reference trace, so it is a reference-validation miss, not a distillation one;
  we will fix the task and tighten the validator"*
- **result:** **positive** — the gate is implemented, enforced at generation time, and the
  class of tasks it governs is now measured: 104 of the 750 evaluation-slice tasks
  (13.9%), which are 4.3× more likely to be unsolvable by any model and account for
  40.7% of the never-solved wall. Removing them changes **no** model's rank.

---

## 1. Question

The distiller-fidelity audit reported in the rebuttal found one spec in 100 whose
required effect was never executed in its own reference trace. We attributed that to
reference validation rather than distillation: the explorer *claimed* success, and
nothing downstream checked the claim against the effects the task requires.

**Q.** If we require a claimed-successful exploration to actually produce every effect
its distilled task demands, how much of the corpus fails, and what does that failure do
to reported results?

## 2. What was wrong

Before this step the only pre-distillation gate was `successful_tool_calls == 0`
(`dmcp/cli.py`) — the explorer's own self-report. A deterministic self-consistency
screen did exist (`gold_unsatisfied_tool_effects`), but it was

1. **narrow** — it saw `tool_effect` checkpoints only, so a spec whose reference never
   produced a required *value* passed it;
2. **post hoc and advisory** — it ran in `dmcp validate` and in the cleanup/merge
   scripts, never in the generation path, and its own docstring says it "does NOT
   delete specs".

So an exploration could be recorded as successful, distilled into a task demanding an
effect it never produced, and released.

## 3. What changed

`dmcp.evaluator.reference_unsatisfied_checkpoints(spec, reference)` — the reference must
satisfy **every** required checkpoint of its own spec under Tier-1, `value_produced`
included. This is the narrow measured invariant we committed to in the rebuttal: *every
required checkpoint is grounded in a successful call in its own trace.*
`state_condition` checkpoints are skipped rather than failed (Tier-1 cannot observe
external state offline; the released corpus contains none).

It is enforced where the claim is made — in `dmcp generate`, before the spec is written;
a rejected exploration is counted and reported. The `dmcp validate` screen, the corpus
filter (`scripts/clean_corpus.py`) and the HF merge (`scripts/merge_to_hf.py`) were
widened to the same predicate. Regression tests: `tests/test_self_consistency.py`
(a claimed-successful exploration — `outcome=success`, one successful call — whose spec
demands a value the reference never produced is rejected, and the old narrow check is
pinned as *not* catching it).

## 4. Method

Deterministic; no LLM, no network. Applied to the released corpus (1,845 specs, 2,051
reference traces) and to the released leaderboard verdicts (8 models × 750 tasks × 3
repeats = 18,000 runs).

```
uv run python scripts/reference_gate_audit.py \
    --specs hfdl/specs.jsonl --traces hfdl/traces.jsonl \
    --verdicts hfdl/leaderboard_e8.10d/verdicts \
    --out docs/experiments/e9.10_numbers.json
```

**Pre-registered decision rule** (fixed before the pass-rate association was computed,
after the bucket counts): ship the gate only if flagged tasks are *materially harder to
solve* than reference-consistent ones — non-overlapping 95% Wilson intervals on the
never-solved rate. If the intervals overlap, the gate is flagging noise and must not
reject specs at generation time. Additionally, report the leaderboard with flagged tasks
removed; **if any model's rank changes, say so.**

## 5. Data

### 5.1 What the gate flags (1,845 released specs, all with a reference trace)

| bucket | specs | share |
|---|---|---|
| reference satisfies its own spec | 1,578 | 85.5% |
| `value_nowhere` — value in no successful result and no final message | 103 | 5.6% |
| `value_misscoped` — value present in the reference, not where the checkpoint scopes it | 137 | 7.4% |
| `no_final_message` — trace records no final message; status unknowable | 27 | 1.5% |
| **flagged, total** | **267** | **14.5%** |

`tool_effect` failures: **0** — the released corpus was already filtered by the narrow
check, which is exactly why the widening was needed to see anything.

### 5.2 Flagged tasks are the wall (750-task evaluation slice, 8 models × 3 repeats)

| group | tasks | runs | pass rate | never solved by any model | 95% CI |
|---|---|---|---|---|---|
| reference-consistent | 646 | 15,504 | 55.2% | 13.3% | [10.9, 16.2] |
| flagged by the gate | 104 | 2,496 | 11.9% | 56.7% | [47.1, 65.8] |

The intervals do not overlap. Flagged tasks are 13.9% of the slice and **40.7% of the
never-solved wall** (59 of 145 tasks no model ever solved).

### 5.3 Leaderboard robustness (flagged tasks removed)

| model | pass, all 750 | pass, kept 646 | pass^3, all | pass^3, kept |
|---|---|---|---|---|
| qwen/qwen3.7-max | 58.9 | 66.4 | 51.2 | 58.5 |
| z-ai/glm-5.1 | 58.0 | 65.1 | 50.3 | 57.0 |

## 6. Result and interpretation

**Positive.** The decision rule is met with room to spare, so the gate ships and rejects
at generation time.

Reading the two failure buckets:

- `value_nowhere` (103 specs) is the defect as described: a required effect was never
  produced anywhere in the exploration that claimed to have produced it. These tasks are
  unpassable as written and should never have been released.
- `value_misscoped` (137 specs) is a subtler and, for the paper, more interesting
  defect: the effect *was* produced, but the checkpoint demands it in a place the
  reference does not put it — most often a `value_produced` checkpoint scoped to the
  final assistant message whose literal string the reference's own summary never wrote,
  or one requiring several terms in a single tool result when the reference spread them
  across two calls. A checkpoint the reference solution itself fails is not measuring an
  effect; it is measuring wording. That is uncomfortably close to the thing this
  benchmark exists not to do, and it is the strongest internal argument for the gate.

Both buckets sit at 55–61% never-solved, against 13.3% for reference-consistent tasks —
the gate separates broken tasks from hard ones without any model in the loop.

## 7. Limitations — stated plainly

1. **The complementary class is out of reach.** This gate compares a spec against its own
   reference, so it cannot see a spec that *omits* an effect the goal needed: such a spec
   is trivially consistent with its reference. Goals declare no required effects
   (`dmcp/goals.py`), so nothing mechanical can close that half; the human audit remains
   the instrument for it.
2. **The audited item is not identifiable from the repo.** Item-level audit labels are
   held externally (camera-ready item 4.2, blocked), so we cannot point at the specific
   1-in-100 spec and say "this one". What we can say is that its class is now rejected at
   generation time and quantified across the whole corpus.
3. **The released corpus is not re-cut here.** `scripts/merge_to_hf.py` now applies the
   widened gate, so a *future* release excludes these 267 specs; re-cutting the existing
   release would move every reported number and is a separate, deliberate decision. §5.3
   is the robustness statement in the meantime.
4. **`no_final_message` (27 specs) is a recording gap**, not evidence of a missing effect;
   it is reported separately and never conflated with the other two buckets.

## 8. Conclusion

The reference validator now enforces the invariant the rebuttal committed to, at the
point where success is claimed rather than advisorily afterwards. Its cost is bounded and
measured: it would have rejected 14.5% of the released corpus, those tasks are four times
likelier to be unsolvable by any model, and removing them leaves every model's rank
unchanged while raising the whole field. The admitted defect is closed for everything
generated from here on, and bounded for what already exists.

**Reproduce:** the command in §4 (deterministic, ~20 s, no API calls).
